# GenEOL 当前阶段实验方案

> 2026-11-24 已完成服务器实查。当前资源、实际脚本范围和第一轮执行参数以 [服务器基线协议](GENEOL_SERVER_BASELINE.md) 为准；本文保留整体研究阶段设计。

日期：2026-11-24。状态：设计稿，待执行。本文中的阈值为预先提出的验收条件，不是已有实验结论。

## 1. 研究问题和贡献边界

目标：在 STS 质量满足预设容忍度时，减少 GenEOL 的真实端到端时间。

- 算法问题：不同句子是否需要不同的变体数 m？预算决策是否优于固定较小 m？
- 系统问题：在相同生成任务与向量计算下，现有推理特性或自有实现能节省多少时间？
- 联合问题：两者组合后是否仍有实际加速，还是被分轮调度、模型切换抵消？

采用现成 vLLM 特性属于强工程对照。自有贡献应由独立消融支持；不能把库本身的收益全部归为新方法。只有 profiling 显示值得优化的瓶颈后，才决定是否编写算子。

文献与实现：[GenEOL](https://aclanthology.org/2025.findings-naacl.122/)、[官方仓库](https://github.com/raghavlite/GenEOL)。下述自适应规则是本项目候选设计。

## 2. 固定模型、数据与执行定义

生成器 Mistral-7B-Instruct-v0.1；向量模型 Mistral-7B-v0.1。编码器不训练，不使用此前 InfoCSE 的投影、replay 或排序损失。

STS-B：train 5749、validation 1500、test 1379。SICK-R：train 4500、trial 500、test 4927。SICK 必须使用原始英语划分，不能将全部 9927 对当测试集。

- 调试与阈值筛选：训练集内按固定种子划出开发子集，记录重复句子的跨划分情况。
- 主探索评价：STS-B validation、SICK trial。它们也已被反复查看，明确称为探索证据。
- 两套 test 此前已有查看记录；最终锁定配置后可作补充评价，不能声称是从未使用的确认集。若需独立确认，另选未查看的 STS 数据集并在运行前冻结协议。
- 以唯一句子为编码与生成单位，每个数据划分单独统计数量和句对数，避免重复句子造成不公平缓存收益。
- 质量全程使用 0–1 的相关系数尺度。

固定并保存：模型与代码 revision、tokenizer、提示文本与哈希、四类变换及 composition 开关、temperature、top-p、最大生成长度、EOS/截断规则、层、pooling mask、各阶段归一化、随机种子、batch/concurrency、软件版本。

m 表示最终纳入聚合的变体数，不含原句，编码量为 m+1。composition 若增加中间生成，必须计入实际生成请求与 token，不能只数最终 m。官方 CLI 的 num_gens 不应直接当成总 m，先用保存样例核对。

## 3. 阶段 0：流程和显存 smoke test

目标：确认能正确运行，再谈质量或速度。

1. 建独立环境，记录 GPU 型号/显存、CPU/RAM、CUDA/驱动和依赖版本，检查剩余磁盘。
2. 固定抽取 64 个不同长度的训练句子，包含否定、数字、长句等；本阶段不选性能阈值。
3. m=4 与 m=8，先 4-bit、小批量，生成器与向量模型顺序加载。记录量化方法、compute dtype 与实际峰值显存，不能只写“4-bit”。
4. 核查提示、四类变换分配、composition、中间与最终文本、输出截断、池化 token、向量归一化。保存有限可审阅样例。
5. 比较单句/批量编码误差与 padding mask；检查 batch 改变未引入错误。
6. 若可获得更大显存，同一小样本补 BF16；分别比较固定文本的向量差异，以及生成端精度变化。不要将两者混为一个量化效应。

通过条件：无 OOM/NaN、生成和编码流程可审阅、完整计时能复算。失败先修流程，不扩大规模。

产物：environment.json、smoke_manifest.json、smoke_metrics.csv、少量样例及日志。文件名为约定，当前尚无对应可执行入口。

## 4. 阶段 1：固定 m 的质量—成本曲线（下一轮优先执行）

配置 m∈{0,4,8,16,32}。m=0 只编码原句，使用相同编码提示与池化。m=4 起每档均衡包含四种变换；若试 m=2，单独声明变换覆盖不同，不混入主因果比较。

先在训练集内的固定开发子集运行；流程稳定后运行两个开发集，3 个配对生成种子。第一轮保持官方式 HF 流程和同一种精度，不同时更换引擎。

做两种分开的测量：

- 质量曲线：为 m=32 保存生成与向量，按预先固定的变换平衡顺序构造嵌套前缀，得到各 m。用于降低生成随机性并进行离线机制诊断。
- 实际时间曲线：每个 m 从同样的空任务缓存起独立执行；不能将“已经生成 32 条后只取 4 条”的耗时当成 m=4 速度。共享前缀质量与独立执行生成可能因 RNG、batch 而不同，两者分别标识。

每档报告：Spearman、Pearson、配对质量差区间、生成请求数、实际 input/output token、编码句子数、总时长、分阶段时长、峰值显存、每秒原始句子数。

观察点：
- 小 m 是否已经在质量容忍范围内？
- m=16→32 是否仍有稳定收益？
- 生成、编码、模型切换各占多少？
- 若固定 m=4/8 已满足目标，自适应必须进一步击败这一更便宜基线，不能只和 32 比。

阶段门：没有明确边际收益递减或可利用的差异时，暂停复杂自适应，先完成固定预算与系统优化结果。

## 5. 阶段 2：先离线筛查自适应 m

先利用阶段 1 的缓存进行模拟，筛掉没有希望的规则。此阶段只能报告预测质量、预算与 token 节省，不能报告实际在线加速。

候选：每次补充 4 个变体，保持四种变换均衡；检查点 m=4,8,16,32。每轮用原句与已生成变体形成当前聚合向量 u_m。

可先只用一个简单规则：
- drift_m = 1 - cosine(u_m, u_previous)，首次在 m=8 判断。
- 连续两次 drift 小于阈值才停止；否则到 m=32。该规则最早 m=16 停止，明确其预算下限。
- 若探索最早 m=8 的单次判定，单列成不同策略，不能事后混用停止条件。

阈值仅在训练集内开发子集筛选，使用小型预定网格，并保存全部结果；不能用每个句对的人工分数决定其 m。句子预算独立于配对对象，保持可缓存的句向量定义。

对照：
1. 固定 m=8、16、32。
2. 与自适应平均 m 接近的固定预算；必要时在两档间随机混合，期望预算匹配。
3. 与自适应拥有相同 m 分布、但随机分配到句子的预算策略。
4. 自适应规则本身。

报告 m 分布、质量、token 成本、不同长度/否定等预先定义分组的变化。随机分配对照用于判断收益是否真正来自“分给了合适的句子”。

阶段门：若自适应不能胜过同成本固定/随机预算，不进入复杂在线实现。

## 6. 阶段 3：profiling 与推理优化

先 profile 固定 m=8 与32，分别检查生成 prefill/decode、编码 attention/池化、padding、CPU/tokenization、数据传输与模型加载。报告端到端占比，估算瓶颈优化的最高可能收益。

按瓶颈逐项启用可兼容特性：更合理的 batching/长度分桶、成熟 attention 后端、vLLM 连续批处理/前缀缓存等。库版本、量化支持、KV cache dtype 和可用特性在环境搭建时查官方文档并固定。不能默认 HF 的量化配置可原样搬到 vLLM。

先做单项消融，再保留最佳组合。若自定义算子有合理空间：
- 与调优后的 PyTorch/现有后端比较；
- 检查数值误差、不同长度与 padding 边界；
- 同时报算子耗时和完整流水线耗时；
- 若该算子占比很小，优先放弃，不以微基准倍数代替项目收益。

编码端可使用相同缓存文本做严格对照。生成端更换引擎可能改变采样输出，除了相同解码参数还要重测 STS 质量，不宣称逐字一致。

## 7. 阶段 4：实际自适应执行与联合消融

自适应停止若依赖向量，需要在生成与编码间反馈。12 GiB 上两模型通常不能同时驻留，逐句切换可能吃掉全部预算收益。

先采用跨句子的轮次队列：一批句子生成→切换编码→判断哪些句子继续→仅对继续者进行下一轮。统计额外加载、CPU/GPU 传输、同步和调度。若切换代价过高，可探索仅生成侧可获得的预算预测，但应标为新策略，重新评价。

核心 2×2：
| 预算 | 参考实现 | 调优实现 |
| --- | --- | --- |
| 固定 m | F-Ref | F-Opt |
| 自适应 m | A-Ref | A-Opt |

另外保留最佳固定小 m 与预算匹配对照。四配置使用同一 GPU、精度、模型、提示和数据，分别调优可行 batch，记录调优范围。比较公平工作负载下各自最佳可行设置；必要时补同 batch 对照解释来源。

不能假设算法与系统加速倍数可相乘，必须测联合结果。

## 8. 计时与统计协议

- 模型文件已在磁盘：主实验不计网络下载。
- 分别报告进程/模型冷启动时间，以及模型已加载、任务输出缓存为空时的运行时间。
- 两模型切换与自适应决策开销计入实际端到端；初始加载是否计入由计时列明确定义。
- 生成文本或向量已有的回放结果只用于分阶段诊断，不作在线端到端主结果。
- 如启用引擎 prefix/KV 缓存，单独声明冷/热状态；所有待比较策略使用约定一致的预热规则。
- GPU 阶段计时正确同步，端到端使用 wall-clock。主时长包含 tokenization、生成、传输、编码、聚合、决策和调度；保存文件耗时另列。
- 单句延迟与离线吞吐分开测；批处理服务时间不称为在线 p95。
- 质量使用3个生成种子；关键配置再扩展，时间每配置预热后至少5次，交替/随机化运行顺序。记录温度、其他 GPU 进程与每次原始时长。
- 配对句对 bootstrap 用于质量差；句子重复导致相关性，区间应注明条件性，并可补句子分组敏感性分析。报告各生成种子差异，不能把 bootstrap 次数当独立模型运行。
- 所有质量与成本都分别列两个数据集，不能用平均掩盖单集退化。

## 9. 预先提出的验收条件

主质量参照为同精度固定 m=32。建议容忍度 ε=0.005，即 Spearman 0.5 个百分点；执行前冻结，可根据课程目标预先调整一次并记录。

- 非劣判据：候选−参照的配对质量差，其单侧95%下界高于 −ε，两个数据集分别检验；普通差异“不显著”不足以证明非劣。
- 资源目标：端到端时长至少降低20%，作为本项目预设的实用目标，并提供重复测量区间。
- 同时比较最佳合格固定 m；若它更快，自适应不算成功。
- 若仅一个数据集通过，报告适用范围，不称为普遍改进。
- 自适应省 token 但实际更慢：记录负结果，优先考虑无需反馈切换的策略或停止算法线。
- 若成熟优化已消除主要瓶颈，自定义算子不再作为必需项；可保留严谨的系统测量结果，但须如实界定创新程度。

阈值不能在看见开发集结果后反复放宽来宣布成功。

## 10. 建议执行顺序与产物

第一轮只做阶段0、阶段1，不同时开发多个方法。

1. 环境与64句 smoke，校验官方流程、composition 与显存。
2. 在训练集内部开发子集运行固定 m 曲线，确认计时和缓存定义。
3. 两个开发集、3配对种子，完成固定 m 质量与成本报告。
4. 基于缓存试一个自适应规则并加入随机预算对照。
5. profile 明确瓶颈，随后做调优引擎与联合2×2。

建议产物：每次运行 config.json、environment.json、manifest.json、metrics.csv、timings.csv；逐句记录 m、token 数、停止原因、句子哈希与缓存状态。生成文本与向量本地保存，轻量汇总经审阅后入库。

拟建代码模块：data、generate、encode、aggregate、budget、benchmark、report；入口 smoke、fixed-m、adaptive、profile。它们是待实现设计，当前不提供虚构运行命令。
